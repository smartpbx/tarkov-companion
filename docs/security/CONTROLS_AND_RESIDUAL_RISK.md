# Controls and residual-risk register

Evidence tiers are defined in `METHODOLOGY.md` and used exactly as defined there:
**Implemented / Reviewed / Tested (automated) / Tested (manual) / Planned**. No row below claims
a tier stronger than what this pass actually did.

**No unresolved High or Critical row may be silently accepted.** Every High/Critical row states an
acceptance decision explicitly. Where this pass could not reach a decision (owner not yet
assigned, verification not yet run), the row says so plainly rather than defaulting to "accept."

## Open findings

| RISK-RELAY-NO-RATE-LIMIT | **Medium** | ABUSE-RELAY-PUBLIC-ENDPOINT-DOS | None. `/catalog`, `/landmarks`, `/search`, and `/state` (both directions) have no request-rate limiting in `Program.cs`; only `/report` has one, via `ProblemReports.IsRateLimited`. The internet-facing address sits behind a Cloudflare hostname (`docs/OPERATIONS.md`), which may absorb some volumetric abuse, but the LAN address (`10.10.10.80:8090`) does not, and Cloudflare in front of the public hostname is not itself an application-level rate limit on these routes. | Reviewed | An anonymous actor can generate sustained load against the relay process and, via `/catalog/{mode}/{endpoint}` cache misses, pressure `json.tarkov.dev` as an amplification path. Blast radius is availability, not confidentiality or integrity — the relay holds no accounts and members already treat it as best-effort infrastructure the client falls back away from (`CatalogMirror.cs` remarks: "must never become a dependency"). | **Defer.** Recommend adding `Microsoft.AspNetCore.RateLimiting` (already in the ASP.NET Core shared framework, no new dependency) scoped per-IP on the public GET routes before the v2 gateway (#304) increases relay reliance. Owner: relay-owning agent for #310. Tracked as a v2 hardening item, not a phase-1 blocker, because no confidentiality or integrity boundary is crossed. |
| RISK-RELAY-KEY-BRUTEFORCE | **Medium** | ABUSE-RELAY-WEAK-KEY-GUESS | `GroupKey.MinimumLength = 8` is the only defense; explicitly documented as *not* access control by its own source comment ("That is not access control, since there is nothing to check against; it stops somebody believing `a` keeps strangers out.", `GroupKey.cs`). No attempt counter, no per-IP lockout, no exponential backoff exists anywhere in the relay. | Reviewed | On an *open* (unregistered) relay this is close to by-design — `docs/GROUP_RELAY.md` states an open relay serves anybody's key. On a *closed* relay (operator has registered rooms), a guessed key for a non-registered room is refused with 403 by `RelayAccess`, so the practical exposure is bounded to relays an operator has not yet locked down, or to guessing a key for a room that *is* registered. | **Accept, with a documentation gap to close.** The design intent (key length is a typo-guard, not access control; real access control is registration) is correct but is not stated as plainly in `docs/GROUP_RELAY.md`'s "Who may have a room" section as it is in `GroupKey.cs`'s own comment. Recommend a doc cross-reference in a follow-up pass; not a code change. Owner: docs follow-up, no urgency — this is a documentation clarity gap, not a control gap. |
| RISK-RELAY-CLIENT-TRUST | **Low** | ABUSE-RELAY-STALE-FRESHNESS | None. `positionAge` is entirely client-computed and reported; the relay never cross-checks it against `sinceSeconds` (server-set, from when it last heard from the member at all) or any other server-observed signal (`docs/GROUP_RELAY.md`). | Reviewed | A member can misrepresent how fresh their own reported position is. Effect is bounded to how *that member* is perceived by squadmates — it cannot be used to spoof another member's data (that is RISK-RELAY-IDENTITY, a distinct case) or to affect the room's integrity beyond one entry. `docs/GROUP_RELAY.md` already documents the parallel, real failure mode this design accepts (a crashed client's position "freezes and the marker reads fresh for the full three minutes"), so misrepresenting one's own freshness is a strict subset of a gap the design already lives with. | **Accept.** The relay has no way to independently verify a client's capture time without trusting the client in the first place — there is no lower-trust alternative available given the project's read-only, client-reported architecture. Consistent with the relay holding "no accounts and no identities" by design. No control proposed. |
| RISK-RELAY-MARK-CAP | **Low** | ABUSE-RELAY-WAYPOINT-FLOOD | The 60-waypoint / 30-ping per-room cap itself, which is a resource bound, not an abuse-specific one — eviction is oldest-first with no distinction between a legitimate and a flooding client (`docs/GROUP_RELAY.md`, "Limits"). | Reviewed | A member (or anyone holding the room's key) can evict a squad's real waypoints by posting enough spam ones in a burst. Requires already holding a valid key for the target room — same precondition as RISK-RELAY-IDENTITY — and the cap itself bounds the damage to "the plan is gone," not any data exposure or persistent compromise; replacing a lost plan costs the squad re-marking, not a security remediation. | **Accept.** The cap exists specifically so "somebody leaning on a mouse button loses their stalest plan rather than being refused or filling the server" (`docs/GROUP_RELAY.md`) — this is a stated, deliberate trade of resource-boundedness over abuse-distinction. Revisit only if #310's admin rebuild adds a per-member or per-IP sub-limit within the room cap. |
| RISK-RELAY-IDENTITY | **Medium** | ABUSE-RELAY-NAME-COLLISION, ABUSE-RELAY-LEAVE-WRONG-NAME | None beyond "last write wins" on display name. No per-member token or session; `docs/GROUP_RELAY.md`'s own rationale for having no identities is stated ("A server that tracked who owned what would need identities, and this one deliberately has none.") for *marks*, but the same absence also applies to `/state` publishing, where it has a different consequence: name collision. | Reviewed | Any member of a room (holding the same group key) can silently take over another member's displayed marker by publishing under their exact name. Bounded to members who already hold the room's key — this is not reachable by ACT-5 without first solving RISK-RELAY-KEY-BRUTEFORCE or being a legitimate member. Within a group of people who trust each other enough to share a key, this is a low-likelihood but real griefing/confusion vector, and matches a documented rough edge (`docs/GROUP_RELAY.md`'s own callout about the rename case). | **Accept.** This is a consequence of the relay's deliberate no-identity design, which is a documented product tradeoff, not an oversight. No control is proposed for phase 1. If a future pass decides per-member session tokens are worth the complexity they were designed away from, that is a product decision for #310, not a security-only call. |
| RISK-CATALOG-INTEGRITY | **Medium** | ABUSE-CATALOG-UPSTREAM-TAMPER | TLS to `json.tarkov.dev` (transport integrity only). `CatalogMirror`'s SHA-256 tag is computed from whatever upstream returned, so it proves consistency between the mirror and its clients, not authenticity of the upstream payload itself. No signature or pinned hash from a second, independent source. | Reviewed | Item/quest/map/trader data manipulated at the source (or on a compromised path with a validly-issued cert) reaches every client of an affected relay, and every desktop client that fetches upstream directly has the identical exposure with no mirror in between (`docs/DATA_SOURCES.md`). This affects gameplay-advisory data (prices, requirements, extract lists) — not the anti-cheat boundaries, since the strategy/prediction engine already labels this data as modelled/public rather than live (`docs/SAFETY.md`). | **Accept.** `json.tarkov.dev` is the project's chosen primary source per `AGENTS.md` rule 11, with no first-party alternative documented. Upstream integrity is outside this project's control surface; the residual risk is that manipulated catalog data could mislead a player's in-raid decisions, which is a data-quality risk, not a security compromise of the player's system. Revisit if `docs/DATA_SOURCES.md` ever adds a second source that could be cross-checked. |
| RISK-UPDATE-CHANNEL-TRUST | **High** | ABUSE-RELAY-UPDATE-DOWNGRADE | Checksum verification against the currently-published `SHA256SUMS` file (`RelayUpdate.cs`), plus a publish pipeline that refuses to publish a version below what is live (`docs/OPERATIONS.md`) and a rollback on failed `/health`. No anti-downgrade check exists in `RelayUpdate` itself — it trusts whatever checksum the release host currently serves as "the newest," with no independently-stored minimum version to compare against. | Reviewed | If an attacker can make `RelayUpdate` fetch a stale-but-otherwise-legitimately-signed `SHA256SUMS.txt` (compromising the release host, its DNS, or the GitHub account that publishes it), a relay could be steered to install an older, potentially-vulnerable build whose checksum genuinely matches an artifact GitHub really published in the past. This requires compromising the release *pipeline or host*, not the relay itself — same actor tier as a full supply-chain compromise (ACT-8), for which the desktop's own updater has the identical structural exposure. | **Not yet decided — flagged for #317's full pass.** This crosses into #317's "cryptographic operations... integrity verification" and "rollback safety" acceptance criteria directly, and needs an owner who can weigh in on whether pinning a monotonic version (not just a checksum) on the update client is worth the added state. Recorded as **open, High severity, no acceptance decision** rather than silently accepted — see `PHASE_STATUS.md`. |
| RISK-DPAPI-SAMEUSER | **Low** | ABUSE-DPAPI-SAME-USER-MALWARE | DPAPI `CurrentUser` scope (`WindowsDpapiSecretStore.cs`). Correctly used for its actual threat model (a different OS user, or the disk read offline) — this is not a defect in the implementation. | Reviewed | Malware already running as the player recovers the TarkovTracker token exactly as the legitimate app would. This is DPAPI's documented threat model, not a gap specific to this project — no local-secrets API on Windows defends against code already running as the same user without additional OS-level isolation (credential guard, a hardware-backed key, etc.) that this project does not attempt. | **Accept.** Matches the sensitivity of the asset: a TarkovTracker read-only progress token, not a payment credential or the group key. Consistent with `docs/adr/0006-optional-tarkovtracker-read-adapter.md`'s scoping of that integration to read-only, user-initiated actions. No action proposed. |
| RISK-TABLET-NO-SCOPING | **Low** | ABUSE-TABLET-KEY-LEAK | None — the group key is the only credential, by design (`docs/GROUP_RELAY.md`, "one key is both which group you are in and proof you belong"). | Reviewed | A leaked or lost tablet exposes full room read/write until the group rotates its key. Bounded blast radius (one group, one room, no cross-group exposure, no access to A-1/A-2/A-4 which never leave the desktop), and rotating a group key is a one-line UX action already supported (typing a new key). | **Accept.** Consistent with the relay's stated design ("no accounts and no identities beyond the display name you send"). Revisit only if #310's relay-admin rebuild introduces per-device scoping as a feature, at which point this row should be re-opened against the new design rather than assumed solved by it. |
| RISK-ANTICHEAT-REVIEW-DISCIPLINE | **Medium** | (process finding, not a single abuse case — see `ANTI_CHEAT_REVIEW.md` boundaries 5, 6, 8) | `ANTI_CHEAT_REVIEW.md` shows three of the eight immutable boundaries (no automation, no enemy tracking/ESP, honest modelled intelligence) have no `audit-safety.sh` pattern-level backstop — they hold today by architecture and code-review discipline only, because they are data-modeling or behavioral boundaries a grep cannot express. | Reviewed | A future feature could violate boundary 5, 6, or 8 without tripping any automated check, and would only be caught by a human or agent reviewer reading the diff against `docs/SAFETY.md`. This is the exact gap #305 (health/character recognition) and #311 (historical-traffic datasets) will each need to close deliberately, since both introduce new evidence surfaces these three boundaries govern. | **Not yet decided — flagged for the integration owner.** Recommend each of #305 and #311 add a targeted deterministic test asserting the specific new surface cannot express a live-enemy or live-presented-as-live concept (matching the existing pattern `docs/SAFETY.md` cites: "Deterministic tests assert that strategy inputs have no live-enemy concept"), reviewed at PR time against this row rather than solved generically here. |
