# Cryptography, secrets, transport, and updates audit

Issue [#317](https://github.com/smartpbx/tarkov-companion/issues/317), adversarial-review lane. This is a source-grounded, static review of commit `d59d136`; it did not run a relay, desktop updater, network attack, build, or test suite. Evidence terminology follows [the security methodology](../METHODOLOGY.md): every code/configuration claim below is **Implemented + Reviewed**, while named tests are only evidence of their existence unless an exact passing CI run is recorded separately.

## Scope and conclusions

The project uses suitable primitives where it owns the operation: OS CSPRNG for generated group keys, SHA-256 for a non-secret room identifier and artifact integrity, DPAPI `CurrentUser` for the optional TarkovTracker bearer token, and fixed-time comparison for the relay admin key. Those choices do **not** turn a reusable group key into a password-authenticated protocol, make a TLS-terminating relay blind to that key, or authenticate an artifact whose checksum arrives from the same mutable release channel.

No new risk ID is created. The actionable findings reconcile to the existing register: `RISK-RELAY-KEY-BRUTEFORCE`, `RISK-RELAY-KEY-DISCLOSURE`, `RISK-GROUP-KEY-LOCAL-EXPOSURE`, `RISK-DPAPI-SAMEUSER`, `RISK-UPDATE-CHANNEL-TRUST`, `RISK-ADMIN-KEY-TIMING`, and `RISK-TARKOVTRACKER-REDIRECT`.

## Cryptographic and protocol observations

| Subject | Evidence | Assessment |
| --- | --- | --- |
| Entropy and encoding | `GroupRoomRegistry.cs`: CSPRNG 16 bytes; alphabet length is 32, which divides 256 exactly, so `% 32` introduces no modulo bias. | Positive control. Add a deterministic shape/uniqueness test around generated keys; no random-output assertion should be used. |
| Group-room derivation | `GroupKey.cs`: unsalted SHA-256 over normalized key, truncated to 128 bits. | Adequate collision resistance for a room identifier. It is not a password KDF, verifier, MAC, or proof-of-possession protocol; offline guesses remain cheap if hashes/keys are exposed and online guesses are unthrottled. This is `RISK-RELAY-KEY-BRUTEFORCE`, not a separate hash defect. |
| Secret comparison | `RelayAdmin.cs`: `FixedTimeEquals(UTF8(provided), UTF8(secret))`. | Correct byte comparison for same-length candidates. It has no key length policy and may disclose length; retain the register's regression caveat. Group keys are not compared with a stored verifier, so fixed-time comparison is inapplicable there. |
| KDF/encryption | No password KDF, HMAC, AEAD, nonce, signature verification, certificate pinning, or independent public key is implemented for group/admin/update credentials. DPAPI supplies encryption/authentication under the Windows user boundary for only the TarkovTracker token. | This accurately describes the product boundary; adding a local KDF alone would not solve relay replay or compromise. |
| Replay | Any captured group/admin header can be replayed until changed. Group state has no nonce, sequence, expiry, or member session identity; replayed state can replace a display name. | `RISK-RELAY-KEY-DISCLOSURE` and `RISK-RELAY-IDENTITY` already cover this. A future protocol needs scoped, expiring device/session credentials and replay binding. |
| TLS trust versus end-to-end secrecy | .NET/Browser HTTPS rely on normal platform certificate validation. `GroupSharingSettings` accepts local/LAN HTTP; tablet and admin inherit whatever origin the operator opened; service binds HTTP on all interfaces. | TLS authenticates/confidentially protects the client-to-accepted endpoint hop. It does not authenticate a user beyond the reusable header and does not conceal the key/content from the endpoint that terminates TLS. |

## Package and update path

| Consumer | Current chain and cache/artifacts | Integrity / downgrade / rollback assessment |
| --- | --- | --- |
| Desktop | `VelopackUpdateGateway` uses pinned `Velopack` **1.2.0** and `GithubSource` for the `dev` pre-release. Packaging produces Velopack feed/packages plus `VELOPACK-SHA256SUMS.txt`; the app source does not read that checksum file. Velopack's local download/apply cache and signature behavior were not independently evidenced from the pinned package/source in this pass. | The publishing workflow serializes, verifies Windows before publish, publishes packages before feed metadata, and rejects a lower `update.json` version. That protects normal workflow ordering, but it is not an independently anchored client acceptance rule. Project source has no minimum accepted version, rollback decision, pinned signing key, or explicit feed/artifact signature verification. A channel attacker can present mutually consistent stale/malicious feed and artifact material. |
| Relay | `tarkov-group-update.sh` downloads `GROUPSERVER-SHA256SUMS.txt` and archive from the same GitHub `dev` release, SHA-256 checks before unpacking, copies prior `/opt` tree, restarts, and health-checks localhost. State stores `INSTALLED_SHA256`, `REFUSED_SHA256`, and request marker outside the replaced tree; self-update units are installed only after health succeeds. | Same-channel checksum detects corruption, not release-channel substitution. A changed older checksum is accepted: no semantic version, commit, pinned minimum, or monotonic checksum history exists. Failed health rolls back code and suppresses retry of that exact checksum, but does not authenticate health response beyond loopback or prove migration/state compatibility. `REFUSED_SHA256` is availability-loop prevention, not anti-rollback. |
| Release pipeline | `windows-verify.yml` scopes `contents: write` to publish, excludes PR publishing, rejects older `update.json`, uploads payload before feed files, then deletes superseded package artifacts. Archive packaging is reproducible and checksums are emitted. `update.json` and legacy `SHA256SUMS.txt` are release audit metadata. | These are valuable operational controls and cache-consistency precautions. They do not create a client-verifiable signature/root of trust; deleting older Velopack packages also constrains client rollback/recovery availability without an explicitly reviewed policy. |

## Findings and release disposition

All entries are **Implemented + Reviewed** static evidence, not penetration-test or passing-run evidence. “Exact verification” is the minimum evidence required before changing the listed disposition; it intentionally does not claim those checks ran here.

| Finding / scenario | Severity | Existing ID, residual risk, disposition and owner | Exact verification |
| --- | --- | --- | --- |
| A user chooses `password1` (valid at eight characters); an actor sends guesses to `/state` and distinguishes a live/open room from empty or a closed allowlist from 403. SHA-256 is fast and no rate control/session proof exists. | **High** | `RISK-RELAY-KEY-BRUTEFORCE`. Full room read/write and name replacement after one guess. **Mitigate; not release-acceptable for v2. Owner: #304/#310.** | Add unit tests that generated keys have the expected 19-character grouped shape (16 symbols from the 32-symbol alphabet plus three separators) and tests/integration fixtures proving per-IP and per-room throttling/backoff; perform an authorized rate-limit test against a staging relay and record exact CI/staging run. |
| A same-LAN actor observes accepted HTTP, or a compromised TLS endpoint records `X-Group-Key`/`X-Admin-Key`; it replays the reusable header to read/write the room or admin APIs. | **High** | `RISK-RELAY-KEY-DISCLOSURE`. TLS endpoint trust is only hop security, not E2E secrecy. **Mitigate; release-blocking for v2. Owner: #304/#310.** | Reject HTTP for every non-loopback group/admin/tablet origin (including DNS rebinding/private-name cases), test that policy at the request boundary, and execute a staging negative test showing plaintext endpoints cannot authenticate.
