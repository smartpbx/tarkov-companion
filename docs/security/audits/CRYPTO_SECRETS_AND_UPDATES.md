# Cryptography, secrets, transport, and updates audit

Issue [#317](https://github.com/smartpbx/tarkov-companion/issues/317), adversarial-review lane. This is a source-grounded, static review of commit `d59d136`; it did not run a relay, desktop updater, network attack, build, or test suite. Evidence terminology follows [the security methodology](../METHODOLOGY.md): every code/configuration claim below is **Implemented + Reviewed**, while named tests are only evidence of their existence unless an exact passing CI run is recorded separately.

## Scope and conclusions

The project uses suitable primitives where it owns the operation: OS CSPRNG bytes for generated group keys, SHA-256 for a non-secret room identifier and artifact integrity, DPAPI `CurrentUser` for the optional TarkovTracker bearer token, and fixed-time comparison for the relay admin key. The current 31-symbol group-key encoding is slightly biased, so this review does not call its output uniform or exactly 80-bit. Those choices do **not** turn a reusable group key into a password-authenticated protocol, make a TLS-terminating relay blind to that key, or authenticate an artifact whose checksum arrives from the same mutable release channel.

The actionable findings reconcile to `RISK-RELAY-KEY-BRUTEFORCE`,
`RISK-RELAY-KEY-DISCLOSURE`, `RISK-RELAY-IDENTITY`,
`RISK-GROUP-KEY-LOCAL-EXPOSURE`, `RISK-DPAPI-SAMEUSER`,
`RISK-UPDATE-CHANNEL-TRUST`, `RISK-ADMIN-KEY-TIMING`, and
`RISK-TARKOVTRACKER-REDIRECT`. Wave 2 adds the distinct stable IDs
`RISK-GROUP-KEY-GENERATION-BIAS`, `RISK-ADMIN-KEY-BRUTEFORCE`,
`RISK-DIAGNOSTIC-CHANNEL-RETENTION`, and `RISK-RELAY-UPDATE-STATE`; their abuse cases,
owners, dispositions, and exact verification are canonical in
[`../ABUSE_CASES.md`](../ABUSE_CASES.md) and
[`../CONTROLS_AND_RESIDUAL_RISK.md`](../CONTROLS_AND_RESIDUAL_RISK.md).

## Secret and key lifecycle

| Material | Creation / derivation | At rest | In transit / logging | Rotation, revocation, deletion | Review result |
| --- | --- | --- | --- | --- | --- |
| Group key | An operator-generated key uses `RandomNumberGenerator.GetBytes(16)` and maps each byte with `% 31` into `GroupRoomRegistry.Generate`'s 31-symbol alphabet. The result is 16 symbols plus three separators (19 visible characters), but is not uniform: indices 0–7 occur 9/256 and the other 23 occur 8/256. Its alphabet ceiling is about 79.27 bits and its min-entropy is about 77.28 bits, not exactly 80. User-supplied keys need only eight non-space characters. `GroupKey.RoomFor` trims then hashes with SHA-256 and retains 128 bits (32 hex characters). | Desktop plaintext `Config/group.json` via `JsonFileGroupSettingsStore`; tablet `localStorage["key"]`; derived room IDs persist in `rooms.json`/marks. The admin create-room response returns a newly generated plaintext key once; later admin views return only room IDs. | Every group request has plaintext `X-Group-Key`; the relay parses it before hashing. Stock desktop logs success/failure without the value; it does log the server exception, so future exception formatting remains a redaction boundary. TLS protects the hop only; direct local/LAN HTTP and a TLS-terminating relay can read/replay it. | Generated value is returned once in `POST /admin/rooms`. No automatic expiry, per-device credential, revocation, or server-side rotation. Changing a group key makes a new room and requires every member to migrate; settings overwrite/turn-off removes local use but does not revoke copied values. | Generated keys remain impractical to exhaust despite the small bias, accepted as `RISK-GROUP-KEY-GENERATION-BIAS`; the fallback shared passphrase model, plaintext storage, replay, and no device revocation remain the separate High/Medium findings below. |
| Relay admin key | Externally provisioned `TARKOV_RELAY_ADMIN_KEY`; no repository creator, entropy policy, or rotation mechanism. | GitHub Actions secret and the CT 115 systemd drop-in documented in `OPERATIONS.md`; browser retains it in tab-scoped `sessionStorage`. | `X-Admin-Key` is compared with `CryptographicOperations.FixedTimeEquals`; it is sent by same-origin admin page and relay-watch. HTTPS protects an authenticated endpoint hop, but direct HTTP exposes it; the relay/process necessarily sees it. No intentional value logging found. | Rotation is an out-of-band change in both deployment locations; no overlap/key-id/revocation audit trail. Browser session storage dies with its tab, not necessarily on a shared unlocked session. | Fixed-time comparison is correct for equal-length values; lifecycle and HTTP exposure are already encompassed by `RISK-RELAY-KEY-DISCLOSURE`; length timing caveat remains `RISK-ADMIN-KEY-TIMING`. |
| TarkovTracker bearer token | User supplies a mode-scoped token; policy validates form/mode before request. | `WindowsDpapiSecretStore` encrypts a UTF-8 copy with DPAPI CurrentUser and fixed application entropy, atomically moves the protected file, and zeroes byte buffers it owns. Filename is SHA-256 of a non-secret reference. | Only `https://api.tarkovtracker.org/token` and `/progress`, in `Authorization: Bearer`; redirects are disabled/rejected and errors/tests redact fixture token values. | Integration service can delete the referenced secret; token rejection marks reconnect required. Server-side issuance/revocation is outside this product. | DPAPI is correctly bounded against other users/offline copies, not same-user code: existing accepted `RISK-DPAPI-SAMEUSER`. |
| CI diagnostic token | `windows-smoke.ps1` creates two GUID-N values for a Windows smoke-process environment variable. Each command also writes its token to a temporary then renamed `*.command.json` file. | Process environment plus the developer-channel command file. The prior environment value is restored; `DiagnosticCommandChannel` normally deletes the command after writing a response, but a crash/interruption can leave the token-bearing file. | Local diagnostic IPC only; no product relay path found. | Environment ends/restores after the smoke script; ordinary command processing deletes the file, without crash-safe cleanup/TTL. | Reviewed as test-only, not a shipped user credential; residual file retention maps to `RISK-DIAGNOSTIC-CHANNEL-RETENTION`. |
| GitHub/runtime tokens | `github.token` is available read-only by default throughout each workflow job; only the publish job receives `contents: write`, while relay-watch receives `issues: write` and the admin secret. The relay itself intentionally has no GitHub token. | GitHub Secrets/Actions runtime, not product storage. | `relay-watch.yml` puts the admin key in a curl header; it does not echo the header value. | GitHub secret rotation is external; write permissions are job/workflow scoped, and the publish job cannot run for PRs. | Appropriate write separation, but token availability, CI log masking, mutable action tags, and GitHub account compromise remain external assumptions. |

## Cryptographic and protocol observations

| Subject | Evidence | Assessment |
| --- | --- | --- |
| Entropy and encoding | `GroupRoomRegistry.cs`: CSPRNG 16 bytes; the literal alphabet has 31 symbols, so `% 31` is biased. Eight indices receive 9 byte values each and 23 receive 8; 16 symbols have an alphabet ceiling of about 79.27 bits and min-entropy of about 77.28 bits. | `RISK-GROUP-KEY-GENERATION-BIAS` accepts the bounded residual for current generated keys, while requiring an unbiased generator during #278 credential redesign. Add deterministic shape/alphabet tests and a generator seam that proves rejection sampling or another unbiased mapping; do not test random uniqueness as proof of entropy. |
| Group-room derivation | `GroupKey.cs`: unsalted SHA-256 over normalized key, truncated to 128 bits. | Adequate collision resistance for a room identifier. It is not a password KDF, verifier, MAC, or proof-of-possession protocol; offline guesses remain cheap if hashes/keys are exposed and online guesses are unthrottled. This is `RISK-RELAY-KEY-BRUTEFORCE`, not a separate hash defect. |
| Secret comparison | `RelayAdmin.cs`: `FixedTimeEquals(UTF8(provided), UTF8(secret))`. | Correct byte comparison for same-length candidates. It has no key length policy and may disclose length; retain the register's regression caveat. Group keys are not compared with a stored verifier, so fixed-time comparison is inapplicable there. |
| KDF/encryption | No password KDF, HMAC, AEAD, nonce, signature verification, certificate pinning, or independent public key is implemented for group/admin/update credentials. DPAPI supplies encryption/authentication under the Windows user boundary for only the TarkovTracker token. | This accurately describes the product boundary; adding a local KDF alone would not solve relay replay or compromise. |
| Replay | Any captured group/admin header can be replayed until changed. Request authentication and the reusable credential have no nonce, sequence, or expiry, and there is no member session identity; replayed state can replace a display name. `GroupRooms` separately expires a member's published state after three minutes of silence, which is not credential expiry or replay protection. | `RISK-RELAY-KEY-DISCLOSURE` and `RISK-RELAY-IDENTITY` already cover this. A future protocol needs scoped, expiring device/session credentials and replay binding. |
| TLS trust versus end-to-end secrecy | .NET/Browser HTTPS rely on normal platform certificate validation. `GroupSharingSettings` accepts local/LAN HTTP; tablet and admin inherit whatever origin the operator opened; service binds HTTP on all interfaces. | TLS authenticates/confidentially protects the client-to-accepted endpoint hop. It does not authenticate a user beyond the reusable header and does not conceal the key/content from the endpoint that terminates TLS. |

## Package and update path

| Consumer | Current chain and cache/artifacts | Integrity / downgrade / rollback assessment |
| --- | --- | --- |
| Desktop | `VelopackUpdateGateway` uses centrally versioned `Velopack` **1.2.0** and passes the repository URL to `GithubSource` with `prerelease: true`. This is a repository prerelease feed, operationally populated by the rolling `dev` release; source does not bind the client to the `dev` tag. Packaging produces Velopack feed/packages plus `VELOPACK-SHA256SUMS.txt`; the app source does not read that checksum file. Velopack's local download/apply cache and signature behavior were not independently evidenced from the pinned package/source in this pass. | The publishing workflow serializes, verifies Windows before publish, and rejects a lower `update.json` version. However, `dist/velopack/*` is one upload glob and includes Velopack feed metadata with packages, so the comment claiming an enforced package-before-feed split is not implemented. Project source has no minimum accepted version, rollback decision, pinned signing key, explicit tag binding, or explicit feed/artifact signature verification. A channel attacker can present mutually consistent stale/malicious feed and artifact material. |
| Relay | `tarkov-group-update.sh` downloads `GROUPSERVER-SHA256SUMS.txt` and archive from the same GitHub `dev` release, SHA-256 checks before unpacking, copies the prior `/opt` tree, restarts, and health-checks localhost. State stores `INSTALLED_SHA256`, `REFUSED_SHA256`, and the request marker outside the replaced tree; self-update units are installed only after health succeeds. | Same-channel checksum detects corruption, not release-channel substitution. A changed older checksum is accepted: no semantic version, commit, pinned minimum, or monotonic checksum history exists. Separately, line 157 writes the new installed stamp before health succeeds; rollback restores the old tree but leaves the rejected stamp. The next run tests installed-before-refused and exits as “already on”, and admin status can falsely name the rejected build. This state defect is `RISK-RELAY-UPDATE-STATE`, distinct from channel authenticity. |
| Release pipeline | `windows-verify.yml` scopes `contents: write` to publish and excludes PR publishing. `scripts/package-windows.sh` runs `scripts/audit-licenses.sh`; the committed `docs/THIRD_PARTY_INVENTORY.json` compares exact resolved NuGet versions and SHA-512 content hashes, so graph drift blocks packaging/publish even though the check occurs after restore/build and `packages.lock.json`/`RestoreLockedMode` are absent. Archive packaging is reproducible and checksums are emitted. | `dotnet tool install --global vpk` is unversioned and outside that inventory; `actions/*@v5` tags are mutable rather than commit-pinned. The Velopack glob does not enforce packages-before-feed publication. The separate CI vulnerability audit is not a dependency of the Windows publish job, so a newly reported vulnerability can fail CI while the Windows workflow still publishes. These controls do not create a client-verifiable signature/root of trust, and deleting older packages constrains rollback/recovery without an explicitly reviewed policy. |

## Findings and release disposition

All entries are **Implemented + Reviewed** static evidence, not penetration-test or passing-run evidence. “Exact verification” is the minimum evidence required before changing the listed disposition; it intentionally does not claim those checks ran here.

| Finding / scenario | Severity | Existing ID, residual risk, disposition and owner | Exact verification |
| --- | --- | --- | --- |
| The generated key maps each CSPRNG byte through `% 31`. An exhaustive attacker can rank the eight slightly more probable symbols first, reducing worst-case min-entropy to about 77.28 bits while leaving exhaustive guessing impractical. | **Low** | `RISK-GROUP-KEY-GENERATION-BIAS`. **Accept for current generated room keys; owner: #278.** Do not call the mapping uniform or 80-bit. The separate High online-guessing risk remains for user-chosen keys and missing throttling. | Add a shape/alphabet test for 16 symbols from the exact 31-symbol alphabet plus three separators. | A user chooses `password1` (valid at eight characters); an actor sends guesses to `/state` and distinguishes a live/open room from empty or a closed allowlist from 403. SHA-256 is fast and no rate control/session proof exists. | **High** | `RISK-RELAY-KEY-BRUTEFORCE`. Full room read/write and name replacement after one guess. **Mitigate; not release-acceptable for v2. Owner: #304/#310.** | Add unit tests that generated keys have the expected 19-character grouped shape (16 symbols from the exact 31-symbol alphabet plus three separators) and tests/integration fixtures proving per-IP and per-room throttling/backoff; perform an authorized rate-limit test against a staging relay and record exact CI/staging run. |
| An operator configures a short or common `TARKOV_RELAY_ADMIN_KEY`; an actor makes repeated guesses against an admin or report route. Any non-whitespace configured secret and any single nonempty header value reach fixed-time comparison, and no rate/backoff control exists. A hit grants room management, update requests, and all retained report bodies. | **High** | `RISK-ADMIN-KEY-BRUTEFORCE`. Fixed-time comparison limits byte-wise timing leakage but does not supply entropy or throttle guesses. **Mitigate before v2 operator use; owner: #310.** | Enforce a generated/high-entropy provisioning policy, generic denial, per-IP/global backoff and auditable rotation. | A same-LAN actor observes accepted HTTP, or a compromised TLS endpoint records `X-Group-Key`/`X-Admin-Key`; it replays the reusable header to read/write the room or admin APIs. | **High** | `RISK-RELAY-KEY-DISCLOSURE`.
