# Working on this

Two people work on this repository, one of them an agent, often at the same time.
These are the rules that keep that from going wrong.

## Trunk

`main` is the trunk and it is always green. Everything the group runs is built from it.

Nothing is pushed to `main` directly. Work happens on a branch and arrives through a pull
request, which merges itself once `linux` is green:

    gh pr create --fill && gh pr merge --auto --merge

Do not wait on it and do not poll it. Start the next thing.

## Branches

One branch per issue, named for it:

    git switch -c 4-floor-follows-height

Short-lived. A branch that cannot be merged today is usually two branches.

## Worktrees

Because two of us work in parallel, use a worktree rather than switching branches under
each other:

    git worktree add ../tarkov-4-floors -b 4-floor-follows-height
    git worktree list
    git worktree remove ../tarkov-4-floors

The database, cache and logs live in `%LOCALAPPDATA%\TarkovCompanion`, outside every
worktree, so two checkouts never fight over them.

## Branches do not have to be current with the trunk

They used to, and the reason was real: two green branches once merged cleanly into code that
referenced a property the other had removed. Green plus green is not green.

The rule cost more than the fault it prevented. With it on, every merge marked every other open
pull request out of date, and each of those owed a full verification run before it could land;
at twenty-seven open pull requests the queue could not drain. The trunk runs the whole suite on
every push, so that collision is still found, a few minutes after the merge instead of before
it, and it is fixed forward with one more small pull request.

## Issues

Everything requested and not yet done is an issue. That is deliberate: this list was kept
in one person's head once, a long session displaced it, and the work quietly stopped
existing until somebody asked what had happened to it.

Close issues from commit messages, so the record of why something changed and the record
of what was asked for stay attached to each other.

## Verification

Nothing here may be built or tested on the maintainer's workstation. It has crashed his
open applications before. Everything runs in GitHub Actions.

- **CI** builds and tests on Linux (and on Windows for pushes to `main`), and runs the dependency, licence, safety
  and secret audits. The licence audit is fail-closed: a new dependency fails the build
  until its licence is reviewed and the inventory regenerated by the License lock workflow.
- **Windows verification** does what no test can. It launches the packaged application on a
  real Windows runner, opens every page, and photographs it. It runs on every push to `main`
  and it is the gate on **publishing**: a build that fails it is never published, because a
  build once passed every test and could not open a window. It does not run on pull requests.
  To see it on a branch before merging, which is worth doing for packaging, installer or
  startup changes and not otherwise: `gh workflow run windows-verify.yml --ref <branch>`.

- **The glance ratchet** (`scripts/sweep-glance.sh`, #712) keeps the Raid page's Now panel
  readable at a glance, and fails rather than warns. In every phase and a worst case, at
  1920x1080 and 1920x1009 with 100, 125 and 150% text, the panel does not scroll, nothing on it is
  cut off and the raid clock is on it once (`NowPanelGlanceTests`); every guess it shows (a counted
  clock, a screenshot's age, an exit never seen offered, a planned stop) has its label on screen;
  every automatic phase switch has a "because" line (`SwitchBecauseGlanceTests`); and the tablet's
  panel fits 1280x800. When content will not fit, the panel folds (`NowPanelViewModel.Fold`);
  change what folds, not the rule.

A pull request merges when `linux` is green. That list lives in `scripts/require-checks.sh`;
run it to see whether the repository still agrees with it.

## Releases

- Every verified build of `main` replaces the rolling `dev` pre-release. That is the group's
  update channel, and the application updates itself from it.
- A tag `v*` cuts a release that stays, for a build worth keeping.

Every published file carries a SHA256. Verify before installing rather than after failing;
that discipline caught a broken install once already.
